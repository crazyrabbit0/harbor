# AGENTS.md

Harbor is a cross-platform Stremio client built with Tauri 2, React, TypeScript, Rust and libmpv. The frontend owns the interface and user interactions; Rust owns native integrations, playback, operating-system behavior and performance-sensitive work. Folder-specific notes live in `src/AGENTS.md` (with `src/lib/i18n/`, `src/lib/games/`, `src/lib/music/`, `src/lib/streams/`, `src/lib/sports/`, `src/lib/manga/`, `src/views/big-picture/`, `src/views/games/` and `src/views/settings/`), `src-tauri/AGENTS.md` (with `src-tauri/games/` and `src-tauri/music/`), `harbor-core/AGENTS.md`, `tests/AGENTS.md`, `scripts/AGENTS.md` and `android-extension-compat/AGENTS.md`.

## The fork is the project now

- The official Harbor project shut down in October 2026: `harbor.site` serves only a sunset page and `github.com/harborstremio/harbor` (remotes `harbor` and `upstream`) returns 404, so fetches from them fail with "Repository not found". `docs/SUNSET.md` lists which features died with Harbor's servers and how to build from a fresh clone.
- `origin` (`crazyrabbit0/harbor`) is the only live remote. `main` is the integration branch: upstream's final `beta-branch` with this fork's work on top. Branch new work from `origin/main` and merge it into `main` with `git merge --no-ff`; there are no upstream PRs to open. `beta-branch` stays frozen at upstream's last beta commit (`8274f054`), and the tag `upstream-main` keeps upstream's old 0.9.21 `main`.
- GitHub refuses Git LFS uploads to a public fork ("can not upload new objects to public fork"), so a large binary cannot live in git here. `libmpv-2.dll` sits on a `libmpv-<sha12>` release of the separate repo `crazyrabbit0/harbor-deps`, which keeps dependency builds off Harbor's Releases page, and `scripts/fetch-libmpv.mjs` downloads it from there, falling back to the byte-identical shinchiro `mpv-dev-x86_64` archive it was taken from. `node scripts/fetch-libmpv.mjs --latest` repins the script to shinchiro's newest `mpv-dev-x86_64` build and writes that DLL. Upload it with the `gh release create libmpv-<sha12> ... --repo crazyrabbit0/harbor-deps` command the script prints before pushing the repin, since that release is the only copy that outlives shinchiro's month of releases. Then update the hash and version in `docs/SUNSET.md`.
- ffmpeg and ffprobe follow libmpv's source on each platform. On macOS they are Homebrew's (`brew install mpv ffmpeg`): `scripts/fetch-binaries.mjs` copies them out of the keg and `scripts/macos-bundle-libmpv.py prepare` relinks them against the bundled libav* libraries in `Frameworks/`, next to the `mpv` helper, so a copy from `fetch-binaries.mjs` alone only runs on the build machine. On Windows they come from one gyan.dev essentials zip pinned by SHA-256 (`FFMPEG_WIN_*` in `fetch-binaries.mjs`), tried from the `ffmpeg-<sha12>` release of `harbor-deps`, then `GyanD/codexffmpeg`, then `gyan.dev/ffmpeg/builds/packages/`. `node scripts/fetch-binaries.mjs --latest` repins it (set `GITHUB_TOKEN` if the anonymous API limit is spent) and prints the `gh release create` command for `harbor-deps`. Linux still takes BtbN's rolling `latest`, unpinned.
- Services on `harbor.site` (updates, accounts, bug reports, sync, relay) no longer answer. TVDB goes straight to `api4.thetvdb.com` with the user's key (`setTvdbKey`/`tvdbGet` in `src/lib/providers/tvdb.ts`), and IGDB goes to `api.igdb.com` with the user's Twitch client ID and secret (`setIgdbCredentials`/`igdbRequest` in `src/lib/games/igdb-client.ts`, which caches the app token until it expires); bring back any other feature the same way, by calling the real service directly.
- Static feeds that `harbor.site` used to host live in the top-level `data/` folder and load from `HARBOR_DATA_BASE` (`src/lib/config/endpoints.ts`, default `https://raw.githubusercontent.com/crazyrabbit0/harbor/main/data`, overridable with `VITE_HARBOR_DATA_BASE`). The URLs only answer once a change to `data/` is on `main`, so test a branch by pointing `VITE_HARBOR_DATA_BASE` at its raw URL. Keep each file in the exact shape its module parses (`anime-awards-source.ts`, `anime-hosted-hero.ts` → `hero-anime.json`, `announcements.ts`, `curated-logos.ts`, `feed/award-winners.ts`, `feed/hero-pool.ts`, `providers/anime-hero-art-static.ts`, `updater/release-notes.ts`, `manga/community.ts` → `manga-sources.json`, `harbor-rank.ts` → `rank/`, `discord/` images). Empty feeds ship as valid empty documents, never invented entries. `data/**/*.json` is in `.prettierignore`.
- The Community theme library is the read-only `data/themes/index.json` plus `.harborstyle` files (`src/lib/theme-store.ts`), added by pull request (`data/themes/README.md`); community collections likewise read `data/collections/index.json` (`src/lib/social/collections-sync.ts`). Theme JS runs with full app rights, so a downloaded or imported theme's script stays off until the user allows it, tied to a hash of the script (`lib/theme-js-consent.ts`). Inline handlers in theme HTML never run under the Tauri CSP; buttons use `data-harbor-action` or `data-harbor-nav`, dispatched through `harborActionFor` (`lib/harbor-chrome-actions.ts`). Theme publishing, ratings and comments needed accounts, so their UI is hidden.
- Harbor accounts are gone: every entry point to them is hidden while `lib/theme-auth.ts`, `lib/account/` and `lib/profile-sync/` stay, and so is UI for the other dead hosts (`bugs.`, `pub.` and `app.harbor.site`: the ad report button, the public relay row, badge and award bundles, ratings, the Discord join buttons). The `"harbor"` phone hand-off step stays parseable for older phones (`HANDOFF_STEPS` in `lib/tv-handoff/handoff-protocol.ts`). Desktop Watch Together invites are a `?harbor-relay=…&harbor-room=…` string for the join box (`buildInviteUrl` in `lib/together/invite.ts`); the browser build still links to its own origin. Nothing in the UI names a backend host, since this fork runs none.
- Trackers call their services directly. Trakt and MAL sign in through this fork's own apps (`HARBOR_TRAKT_CLIENT_ID` in `lib/trakt/config.ts`, Trakt issues it no secret; `HARBOR_MAL_CLIENT_ID` in `lib/mal/config.ts`, App Type "other"). Client IDs are public, so they are compiled in; `VITE_*` overrides them at build time and the user's own app in Settings (`settings.traktClientId`/`traktClientSecret`/`malClientId`, pushed into `lib/trakt/credentials.ts` and `lib/mal/credentials.ts` from `settings.tsx`) overrides both. A Trakt/MAL session stores the `clientId` that issued it; sessions without one came from upstream's apps and keep using upstream's public client ID, since a token only works with its own app. AniList uses the implicit grant on client 42941 (pin page, no secret). Simkl ratings hit `api.simkl.com/ratings` one ID per request.

Known architecture issues not fixed yet (small bugs, native threading, the network layer and large refactors) are listed with file references in `docs/ARCHITECTURE-FOLLOWUPS.md`; remove an item there when you fix it.

## Priorities and working rules

- Correctness and reliability first, then smooth playback and responsive navigation, consistent behavior across Windows, macOS, Linux and TV-style input, and simple, maintainable code. When trade-offs are required, prefer predictable behavior over clever or temporary solutions.
- Read the relevant files before changing them, inspect existing code before adding abstractions, and reuse shared logic instead of duplicating it. Follow the existing naming and code style.
- Keep changes limited to the task: no unrelated refactors, fix root causes rather than adding local workarounds, preserve backward compatibility, and never silently change user-facing behavior.
- Keep components focused and small, and keep business logic outside React components when it can be a reusable module. Keep platform-specific behavior isolated.
- Add comments only when they explain a non-obvious decision. Never expose secrets, tokens, private URLs or user data.

## Architecture

- `src/`: React and TypeScript app. `src/components/` holds reusable UI, `src/hooks/` shared React behavior, `src/lib/` framework-independent modules.
- Navigation is a custom view/frame stack in `src/lib/view.tsx`; there is no router (no TanStack Router or Query, only `@tanstack/react-virtual`). Data fetching is plain `fetch` via `src/lib/safe-fetch.ts` plus module stores in `src/lib/`.
- `src-tauri/`: Tauri app and native Rust (commands, playback, window management, platform code).
- `harbor-core/`: Rust stream parsing and ranking. The app does NOT load it as WASM (CI only checks that it still builds for wasm32): desktop runs its trust, score and rank stages natively through the Tauri command `streams_run_pipeline` (`src-tauri/src/streams.rs`) on streams the TS `parseStream` already parsed, so the Rust parser never runs in the app; without Tauri, or on any invoke error, `src/lib/streams/pipeline.ts` falls back to the TS implementation in `src/lib/streams/` (`parser.ts`, `trust.ts`, `scoring/`), with one `console.warn` per session. Only the episode rule has a shared Rust/TS fixture (see `harbor-core/AGENTS.md`), so any other ranking change in one is not reflected in the other unless you port it.
- Reference repositories for established patterns (don't copy large implementations): Stremio protocol and app behavior <https://github.com/Stremio/stremio-core>, mpv lifecycle and desktop playback <https://github.com/jellyfin/jellyfin-desktop>, Tauri and libmpv integration <https://github.com/MaxMB15/MaxVideoPlayer>.

## Playback, navigation and input

- mpv is the source of truth for playback state; keep the React interface synchronized through events rather than assumptions. Avoid blocking work inside mpv callbacks, and don't mix platform-specific window logic with general playback logic.
- Focus and activation are separate actions: focusing an input must not start editing it, and inputs become editable only after explicit activation. Keyboard, remote and gamepad navigation must behave consistently, and the user's configured hotkeys must be preserved.

## Before finishing a task

- Lint the changed files (`vp check`, see Commands), and typecheck after TypeScript changes with `pnpm run typecheck` (`tsc --noEmit -p tsconfig.json`). Never use `tsc -b` for a typecheck: it emits `vite.config.js` and `vite.config.d.ts` (both gitignored), and writing them restarts the dev server. `tsc -b` belongs only in the `build` scripts. A bare `vite build` prefers that stale `vite.config.js` over `vite.config.ts`, so an ad-hoc build silently ignores config changes; pass `--config vite.config.ts`.
- `pnpm run typecheck:fast` runs the same check with TypeScript 7 (native, about 15 s against about 2 min) through `pnpm dlx --package=typescript@7.0.2`. CI runs both, and the code must pass both. TypeScript 7 rejects `baseUrl` and is stricter about `Uint8Array<ArrayBufferLike>` as a `BlobPart` or `BufferSource`: type byte buffers built from a fresh `ArrayBuffer` as `Uint8Array<ArrayBuffer>`. Never add `typescript@7` as a dependency, even under an alias: its `tsc` bin takes over `node_modules/.bin/tsc`, so `tsc -b` in the build scripts would run 7, and 7 ships no `tsserver.js` for the language server.
- After Rust changes run `cargo check --manifest-path src-tauri/Cargo.toml`. The full Linux binary builds with `pnpm tauri:build:linux-system`.
- Test platform-specific changes on the affected platform when possible, and leave no warnings or errors introduced by the task. If a repository-wide check fails on untouched files, record the baseline and don't reformat or refactor unrelated files.

## Commands

- `vp` (Vite+) is not a package dependency and not installed globally ("'vp' is not recognized"); CI installs it with `voidzero-dev/setup-vp`. Run it through pnpm: `pnpm dlx --package=vite-plus@1.1.0 vp fmt <files>` to format, `vp fmt --check <files>` and `vp check --no-fmt <files>` (same prefix) to check. That is exactly what CI runs on the changed files, followed by `vp run typecheck:fast`, `vp run typecheck` and `vp run test`. The "No config found", "built-in command" and `esbuild` deprecation lines it prints are noise; read the `pass:`/error line.
- Never format with `oxfmt@latest`: it wraps long lines differently from CI's `vp fmt`, and 22 test files formatted with it failed Code Quality. Never pass `--config .oxfmtrc.json` either: that applies the locale-only `quoteProps: "consistent"` override to every file and turns a 10-line edit into a 1,400-line re-quote; `vp fmt` finds the config itself. `oxfmt` wraps long locale entries as `"key":\n    "value",`, so write new long translations that way.
- Files are LF (`core.autocrlf=false` in this repo's `.git/config`). Save edits with LF; `git ls-files --eol <files>` must show `i/lf w/lf`, or the whole file shows as rewritten and is committed with CRLF.
- Single test file: `node --experimental-loader ./scripts/node-test-loader.mjs --test tests/<name>.test.ts`. The loader resolves `@/` to `src/` and extensionless imports, turns image imports into their URL and CSS imports into nothing (as Vite does), and gives `src/` modules an empty `import.meta.env`; plain `node --test` cannot load these files. Node strips types without compiling, so a `.ts` file a test imports directly cannot use TypeScript-only syntax such as constructor parameter properties. Tests are flat `tests/<topic>.test.ts`; harnesses in `tests/helpers/`, `_*.ts` stubs (localStorage, IndexedDB) in `tests/` are excluded from the glob.
- Rust checks without the fetched sidecars: CI sets `TAURI_CONFIG='{"bundle":{"externalBin":[],"resources":[]}}'` for `cargo check` / `cargo test --manifest-path src-tauri/Cargo.toml`. Set the same variable when `pnpm run setup` hasn't been run.
- `harbor-core` CI (run inside `harbor-core/`): `cargo test --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo check --target wasm32-unknown-unknown`. Any clippy warning fails CI.
- Local-only validators (not in CI): `pnpm check:settings` and `check:search` after settings UI/search edits; `node scripts/check-i18n.mjs` after locale edits. `check:tvstrings`, `check:tvinvariants`, `check:tvresources` and `check:orphanstrings` read the Android TV Kotlin shell in `android-native/`, which is gitignored and not in this repo, so they fail with ENOENT on a normal checkout.
- `pnpm test` runs `tests/*.test.ts` AND `tests/*.test.mjs` (~825 + ~30 files) through the loader in one Node process pool with default concurrency. The two colocated `src/lib/providers/tmdb/*.test.ts` sit outside that glob and only run when named explicitly. Test-folder conventions: `tests/AGENTS.md`; scripts: `scripts/AGENTS.md`; `harbor-core/AGENTS.md` covers which Rust half the app actually runs.
- `pnpm run setup` fetches binaries, libmpv, mpv, fonts and stages capstan; `setup:all` is a different set (no capstan) and ffmpeg also has its own `setup:ffmpeg`. `build:desktop` = capstan stage + Pokémon engine stage + `tsc -b` + `vite build` and is what `tauri build` runs; plain `build` skips capstan.
- `ci.yml` runs `cargo check`/`cargo test` on `src-tauri` only when `src-tauri/`, `harbor-core/` or `ci.yml` changed. `harbor-core.yml` tests on Linux, macOS and Windows and also runs `wasm-pack build --target bundler`.
- That `cargo test` step (Code Quality, "Native" job, "Test Tauri application") points `HARBOR_GAME_TEST_ROOT`, `HARBOR_BATTLENET_TEST_ROOT` and `HARBOR_TEST_ROOT` at a fresh `runner.temp` folder; the `games::` fixtures write only there. Set the same three locally (plus `libmpv-2.dll` on `PATH` on Windows, or the test exe dies with `STATUS_DLL_NOT_FOUND`). A green Code Quality run on a docs or frontend push only means the step was skipped. `Swatinem/rust-cache` saves only after a successful job, so until one Native run passes, every run compiles cold (about 27 minutes for `cargo check` plus the test build); the job's 60-minute limit covers that. To reproduce the Linux job, run `cargo test` in an `ubuntu:24.04` container as a non-root user with the step's apt packages; give Docker Desktop at least 8 GB and cap `CARGO_BUILD_JOBS` (about 3), or linking the test binary hangs the engine.

## Dev server and build quirks

- `pnpm dev` runs `scripts/capstan-stage.mjs --dev` first (Java runtime preflight for the extension bridge, always exits 0), then Vite on `127.0.0.1:1420` with `strictPort`, so it fails rather than switching ports if 1420 is busy.
- The React Compiler (`babel-plugin-react-compiler`) runs only on the folders (trailing `/`) and files in `REACT_COMPILER_DIRS` in `vite.config.ts`, with `panicThreshold: "none"` so a component it cannot compile is left as written. Babel runs only on those folders (the `babel` option is a function returning no plugins elsewhere), which halves `vite build` time; `react/compiler-runtime` is listed in `optimizeDeps.include` because the function form hides it from plugin-react. Before adding a folder, run `pnpm check:react-compiler <folder>`: it exits 1 on any component the compiler would skip, on a memo dependency the callback never reads, and on a store hook called only to re-render (`useTop10Version();`), because the compiler keys caches on what the body reads. Read store values through `readAtVersion(version, () => ...)` (`src/lib/read-at-version.ts`) instead. `"use no memo"` opts a component out; keep it for incompatible libraries such as `useVirtualizer`.
- `src-tauri/` is excluded from the Vite watcher, so Rust changes need `pnpm tauri dev`, not HMR.
- `build:tv` / `--mode android` builds `index-tv.html` (`src/main-tv.tsx`) with a `chrome87` syntax floor. Don't use newer syntax in code the TV entry reaches.
- The app also runs in a plain browser. Outbound HTTP goes through `safeFetch`, which rewrites listed hosts to `/api-proxy/<host>/...` off-Tauri. A new third-party host goes into `PROXY_HOSTS` in `safe-fetch.ts` (the production proxy) and into `src/lib/dev-proxy-hosts.json`, which both `vite.config.ts` and `safe-fetch.ts` read for the dev server. `docs/ARCHITECTURE-FOLLOWUPS.md` lists which global `fetch(` calls stay direct and why.
- `hbx.mjs` evaluates JS in the running app over CDP (`127.0.0.1:9333`), which exists only when Harbor starts with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` (`scripts/dev-diag.ps1` sets it for `pnpm tauri dev`). To play a local file without the UI, dispatch `harbor:open-local-file` with `{ detail: { path } }` and read mpv through `window.__TAURI_INTERNALS__.invoke("mpv_get_property", { name })`; judge playback from `time-pos`, since the CDP screenshot never shows mpv's native video window. Use a clip of at least 180 s (`SHORT_PLAYBACK_SEC` in `lib/dead-streams.ts`), or the player treats it as a stub and returns to the picker. If `time-pos` stays at 0 with `AUDCLNT_E_DEVICE_INVALIDATED` in the log, set `audio-device` to a working entry from `mpv_audio_devices` and run `ao-reload`. Read `app_features` rather than the sidebar to see which rooms a build offers (a profile's `navCustomization.hidden` hides tabs too). Kept-alive rooms stay in the DOM under `[data-layer-inactive]`, so filter those out, and never match `aria-label="Close"`: the window's own close button carries it and quits the app.
- A local release build (`target\release\harbor.exe`) shares everything with the installed Harbor: `%APPDATA%\app.harbor` files and the WebView2 localStorage under `%LOCALAPPDATA%\app.harbor\EBWebView`. A branch that migrates stored data (e.g. moves keys out of the settings blob) changes the user's real profile on first launch, and restoring `settings.json`/`secrets.json` alone does not undo the localStorage half. Back up the whole `EBWebView\Default\Local Storage\leveldb` folder too (copy it while no Harbor runs), or test on a copy of the profile.
- Dev and release builds keep separate WebView storage: dev runs on origin `http://localhost:1420`, release on `http://tauri.localhost`, so `pnpm tauri dev` starts with default settings and no watch history. Both still write the shared `%APPDATA%\app.harbor\settings.json` (`settings_write`), so a dev session overwrites the real profile's settings file. Back it up first; to test against the real profile, use a release build.
- Many tests compile a module with a mock `require` that allows only listed imports, so a new import fails them with `Unexpected import`/`Unexpected dependency` until the mock gets an entry; older tests regex-match source text and fail on a rename. `tests/AGENTS.md` covers both and says how new tests are written. `git grep` the old name in `tests/` before renaming in the player hooks.
- The music player harnesses (`music-player-speaker`, `music-quality-player`, `music-preferences`, `music-video-transport-wiring`) spread `tests/helpers/music-player-dependencies.ts` into their mocks; a new import in `src/lib/music/player.ts` goes there once. Tests that evaluate single functions out of `player.ts` (`music-player-source-recovery`, `music-surprise`) list every free name in their own `scope`.
- `tests/helpers/playback-persistence-harness.ts` swaps every import of `use-resume-autosave.ts` for a stub in `dependencies`, so a new import in that hook needs a matching stub there. Tracker sync resolves in a `.then(async …)` chain, so wait with `await new Promise((r) => setTimeout(r, 0))`; two `await Promise.resolve()` calls are not enough.

## Release builds (Windows)

- `pnpm tauri build` stops in `beforeBuildCommand` with `[capstan] no libs at ...android-extension-compat\libs` (exit 1, before any Rust compiles) when the gitignored compat jars are absent. Fetch them (`pnpm run setup` / `android-extension-compat/tools/deps.sh`), or build deliberately without extensions: `HARBOR_CAPSTAN_SRC=<nonexistent dir>` plus `HARBOR_CAPSTAN_OPTIONAL=1`. `OPTIONAL` alone is not enough: it only excuses a checkout with no layer directory at all.
- `vite build` runs the React Compiler over all of `src/views/` and dies with "JavaScript heap out of memory" at Node's default heap (about 4 GB, after 6 minutes); set `NODE_OPTIONS=--max-old-space-size=6144` as CI and the Flatpak manifest's `build-options.env` do.
- Quick frontend-only rebuild of an existing release exe: `pnpm exec vite build --config vite.config.ts`, then `pnpm tauri build --no-bundle --config <file>` where the file holds `{"build":{"beforeBuildCommand":""}}` (pass a file; inline JSON loses its quotes in PowerShell). Rust is cached, so this takes ~5 min, and the exe embeds `dist/`.
- Before building, stop every process whose executable is under `src-tauri\target\release`, not only `harbor.exe`. The build copies sidecars into that folder and fails with `os error 32` (file in use) after several minutes of compiling. A renamed copy (e.g. `harbor.old.exe`) and the `mpv.exe` it spawns lock the folder too. Filter by `ExecutablePath`, never by process name. The user may be watching something, so ask before stopping anything.
- `pnpm tauri build` can rewrite `src-tauri/Cargo.toml`. Check `git diff src-tauri/Cargo.toml` before restoring it: `git checkout -- src-tauri/Cargo.toml` also discards your own uncommitted edits to that file (such as `[profile.release]`).
- A cold release build is ~25 min (~900 crates, 8 threads). Use `--no-bundle` for just the exe, `--bundles nsis` for only the installer.
- Run a release build alone: the fat-LTO link of the `harbor` lib needs more than 5 GB, and next to `cargo test` (the games tests) it died with `rustc-LLVM ERROR: out of memory` (`0xc0000409`) after about 20 minutes. Even alone it needs about 7 GB of free commit (RAM plus page file): with a browser and chat apps open it failed with that error, and with thin LTO with `os error 1455` ("The paging file is too small"). Check `FreeVirtualMemory` in `Win32_OperatingSystem` first, and close apps or grow the page file if it is under 8 GB. Changing `CARGO_PROFILE_RELEASE_LTO` rebuilds every crate cold.
- A git-excluded `.cargo/config.toml` (via `.git/info/exclude`) can set `rust-lld.exe` as the MSVC linker and `[profile.release] incremental = true, codegen-units = 256` for faster local builds. Changing profile settings invalidates the whole release cache once. Delete the file for a build that ships, since 256 codegen units costs some runtime speed.
- `target\release\harbor.exe` is not standalone: it statically imports `libmpv-2.dll` (won't launch without it), finds `mpv`/`ffmpeg`/`ffprobe`/`yt-dlp` and `fonts\`/`resources\` next to itself, and needs `MSVCP140.dll` (installed next to it by the NSIS installer, or the VC++ 2015-2022 x64 redistributable) and WebView2 on the target machine. Distribute the NSIS installer from `target\release\bundle\nsis\` instead.

## Releases

- Every push to `main` (outside docs and markdown) runs the Release workflow (`.github/workflows/tauri-build.yml`). Its first job runs `node scripts/bump-version.mjs --next`: the checked-in version ships as is until a `v<version>` tag exists, after that each push takes the next patch. When the version changes, the bot commits `chore(release): v<x.y.z>` to `main`, so `git pull` before the next push.
- It then builds Windows (NSIS `-setup.exe`), macOS Apple silicon and Intel `.dmg` (both need macOS 15: the bundled Homebrew `libSvtAv1Enc` and `libcrypto` are built for it, and `macos-bundle-libmpv.py` raises the floor to match), Linux x86_64 and arm64 `.deb`/`.AppImage`, and the Flatpak (`flatpak.yml` as a reusable workflow), and publishes them as the GitHub release `v<x.y.z>`. The release body is the commit changelog since the previous `v*` tag, grouped by conventional-commit type (`scripts/release-notes.mjs`), so write commit subjects as user-facing `type(scope): change` lines.
- In-app updates use the Tauri updater against `https://github.com/crazyrabbit0/harbor/releases/latest/download/latest.json`, which `scripts/updater-manifest.mjs` writes into each release for the `-setup.exe`, the two `.app.tar.gz` archives and the two AppImages, with their signatures inline. The signing key is the `TAURI_SIGNING_PRIVATE_KEY` repo secret (no password); its public half is `plugins.updater.pubkey` in `src-tauri/tauri.conf.json`. Losing the private key means every installed copy has to be reinstalled by hand to take updates again. Windows signs `setup.exe` during `tauri build`; macOS signs the archive after the bundle is re-signed and verified, and Linux signs the AppImage after bundling. On Linux only an AppImage (`APPIMAGE` set, reported as `appImage` by `handoff_probe`) shows the in-app updater; `.deb` and Flatpak installs update through their package manager.
- macOS signing reads the optional `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID` secrets. With no certificate or identity the bundle is ad-hoc signed (a warning, not a failure); `APPLE_ID` without `APPLE_TEAM_ID` fails the job on purpose.
- Release and PR builds compile the Pokémon engine with `node tools/pokemon-engine/build.mjs` (.NET SDK `10.0.401`) into `src-tauri/resources/pokemon-engine`; `pnpm run setup` does not. `pnpm dev` and `build:desktop` run `scripts/pokemon-engine-stage.mjs`, which creates the folder empty and warns, so a local build without .NET succeeds and Pokémon save editing reports `pokemon_engine_missing`.
- There is one release channel: the "Get beta updates" toggle is hidden, and the managed `installer/` (Harbor Setup) is no longer built, since its experimental channel and return-to-beta flow ran on `harbor.site`. "Roll back to an earlier build" lists releases from the GitHub API (`src/lib/updater/versions.ts`, which keeps the changelog under `## Changes` and the installer matching `handoff_probe`'s platform key). The unauthenticated API allows 60 requests an hour per IP, so on any API failure it reads the newest 10 from `releases.atom` instead. Builds show the Beta badge only when built with `HARBOR_CHANNEL=beta`. Build feedback opens a prefilled GitHub issue labelled `feedback`.
- Each release body is a `## Downloads` table (`scripts/release-assets.mjs`) followed by `## Changes`. The `.sig` files stay out of the release: `latest.json` carries the signatures inline.
- WinGet (`winget.yml`) submits each release as `CrazyRabbit.Harbor` through the fork `crazyrabbit0/winget-pkgs`. The Release workflow calls it after publishing, because a release created with `GITHUB_TOKEN` fires no `release` event for other workflows; it can also be run by hand with a tag. It needs a `WINGET_TOKEN` repo secret (a classic PAT with `public_repo` and `workflow`) and skips with a warning without one. The action only updates an existing package, so the "Resolve release" step asks the GitHub API for `manifests/c/CrazyRabbit/Harbor` in `microsoft/winget-pkgs` and, while that answers 404, skips with a warning instead of letting the action fail; any other status fails the job. The first version (0.9.206) is microsoft/winget-pkgs#454723, still open (validation passed, awaiting Microsoft's review); once it is merged, every release submits on its own.
- Release `v0.9.132` is upstream's last beta (`8274f054`) with unchanged app code, built from the tag's own commit, which adds only build fixes and a one-off `beta-release.yml`. It is never marked latest and cannot update itself. Its body describes the build instead of listing changes.
- Chromecast launches Google's Default Media Receiver (`CC1AD845`, `"default"` in `rust_cast`). Upstream's own receiver app `120F754D` points at `harbor.site/cast-receiver/`, which is gone.
- Versions are plain numbers (`x.y.z`), since Windows file versions are numeric and reject suffixes like `-cr`. The fork's line starts at `0.9.200`, well past upstream's last beta `0.9.132`. To jump to a new minor, run `node scripts/bump-version.mjs <x.y.z>` and commit; it rewrites `package.json`, both `tauri.conf.json`, both `Cargo.toml` and `Cargo.lock`, and the Flatpak metainfo release.
- The macOS Apple silicon job can end `cancelled` after about 15 minutes with the annotation "The job was not acquired by Runner of type hosted even after multiple attempts". That's GitHub running out of arm64 runners, not a build failure: no step ran. `publish` needs every `build` job to succeed, so nothing is released and the run ends `failure` even though the other platforms built. "Re-run failed jobs" on the same run rebuilds only that job, and once it succeeds `publish` and `winget` run. The same fix applies to an upstream download outage: a Maven Central 504 in `capstan` `tools/deps.sh` (macOS "Tauri build") or a launchpad 503 for `intltool` (Flatpak "Build repository"), and to a macOS job that stops at `Running bundle_dmg.sh` with "failed to run ... bundle_dmg.sh" and no other output (seen once on macOS-Intel; the next two runs passed with no change). A run whose `publish` fails creates no tag, so the next push ships the same version number with both changes.
- The Flatpak builds offline from `flatpak/node-sources.json` and `flatpak/cargo-sources.json`, so adding or bumping a JS or Rust dependency must regenerate them with `flatpak/update-flatpak.sh` in the same change, or the Flatpak job fails (`ERR_PNPM_NO_OFFLINE_TARBALL` for npm) and nothing is released. Adding `babel-plugin-react-compiler` without it blocked v0.9.222. The script needs Linux: in WSL Ubuntu, without sudo, put Node 22 on `PATH` from the nodejs.org tarball and pre-create `.flatpak-work/source-generator/venv` with `virtualenv.pyz` (the distro lacks `python3-venv`). Its last steps need `vp`, `desktop-file-validate`, `appstreamcli` and `flatpak-builder`; once the sources are written those can fail harmlessly, then run `vp fmt flatpak/node-sources.json` on Windows.
- The `.deb` links whichever libmpv soname its runner's `libmpv-dev` provides, so both Linux builds run on Ubuntu 24.04 (`libmpv.so.2`) and depend on `libmpv2` alone; a 22.04 runner links `libmpv.so.1`, which 24.04 and later lack, and the app fails to start. Building there needs glibc 2.39, so `depends` carries `libc6 (>= 2.39)` and apt refuses Debian 12 or Ubuntu 22.04 instead of installing an app that cannot start; raise it with the runner. Check a built package with `readelf -d` (NEEDED) and `objdump -T | grep GLIBC_` against its `Depends`.
- `harbor.exe` imports `MSVCP140.dll`. `pnpm run setup:vcruntime` (`scripts/fetch-vcruntime.mjs`, part of `setup`) copies `msvcp140.dll`, `vcruntime140.dll` and `vcruntime140_1.dll` from the newest Visual Studio `VC\Redist\MSVC\<ver>\x64\Microsoft.VC*.CRT` into the gitignored `src-tauri/vcruntime/`, and `tauri.windows.conf.json` installs them next to the exe, so a PC without the VC++ redistributable still starts Harbor.
- `app-build.yml` compiles Windows, macOS and Linux without installers on pull requests only, since the Release workflow already builds `main`. Keep both Linux builds: the system-library build (`.deb`/`.AppImage`) and the Flatpak sandbox use different toolchains, so either one can break while the other stays green.
- To test a change locally, build `main` (or the feature branch) with `pnpm tauri build --no-bundle` and the capstan variables above, about 7–15 min warm, then launch `target\release\harbor.exe`.

## Pre-commit hook

- `.vite-hooks/pre-commit` runs `vp staged` (`vp check --fix`), so it also needs `vp`. Instead of `--no-verify`, put a shim on `PATH` for the commit: a `vp.cmd` holding `@echo off` and `pnpm.cmd dlx --package=vite-plus@1.1.0 vp %*`, plus an extensionless `vp` holding `#!/bin/sh` and `exec pnpm.cmd dlx --package=vite-plus@1.1.0 vp "$@"` (git runs the hook through its own `sh`). Keep both in the temp dir and delete them afterwards.
